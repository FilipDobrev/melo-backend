# OpenAPI description

A multi-file OpenAPI 3.1 description of the Melo API: 36 path files, 61
components, rooted at `openapi.yaml`. It's the machine-readable counterpart
to [`API.md`](../API.md) at the repo root.

- **API.md** is the prose contract - the one humans (and Claude) read and
  keep authoritative for endpoint-by-endpoint narrative.
- **This folder** is the machine-readable contract - meant for codegen,
  linting, request validation and a Redoc/Swagger preview.

They describe the same API and must never disagree. When you add or change
an endpoint, update both in the same change. `src/__tests__/openapi-drift.test.ts`
(part of `npm test`) enforces the machine-readable half of that: it builds
the real Express app, walks its router stack, bundles this description, and
fails with a readable diff if a mounted route has no matching operation here
or vice versa. It cannot check API.md's prose against the code - that stays
a human/review responsibility.

Where the two ever disagree, or either disagrees with the code, the code
(`src/routes`, `src/dto/*.dto.ts`, service response types) is truth - fix
the docs, don't guess.

## Adding or changing an endpoint

See [`CONVENTIONS.md`](./CONVENTIONS.md) for the step-by-step (file naming,
component reuse, pagination shape, nullable fields, operation IDs, auth,
errors). This file only covers the mechanics of working with the folder day
to day.

## Commands

```bash
npm run openapi:lint      # redocly lint - must pass before committing
npm run openapi:bundle    # bundles to openapi/bundled.yaml (gitignored, generated - don't edit or commit it)
npm run openapi:preview   # serves a Redoc preview at http://localhost:8081
npm run openapi:docs      # builds a standalone HTML file at openapi/docs.html (gitignored, generated)
```

`npm test` also bundles the description on every run (inside the drift
test), so `bundled.yaml` is never something a developer needs to remember
to regenerate by hand before the tests will pass.

### Viewing the documentation

Choose the approach that fits your workflow:

- **`openapi:preview`** - Runs a live-reloading development server while you are editing the API description. Changes appear instantly without rebuilding.
- **`openapi:docs`** - Generates a static, self-contained HTML file you can open directly in a browser, email to someone, or publish to a website without needing a running server.
- **`openapi:bundle`** - Merges all YAML files into a single machine-readable specification for codegen tools and integrations that expect a unified file.

## Layout

```
openapi/
  openapi.yaml       root document: info, servers, tags, security, the paths: map
  CONVENTIONS.md      authoring rules - read this before adding an endpoint
  README.md           this file
  bundled.yaml         generated by openapi:bundle, gitignored
  paths/<tag>/...      one file per path, directory = tag (see CONVENTIONS.md)
  components/
    schemas/           named response/request shapes
    responses/          shared error responses (400, 401, 404, 429, 500, ...)
    parameters/         shared query/path parameters (cursor, limit, ...)
    requests/            shared request bodies
```

`openapi.yaml`'s `paths:` map is the index: every documented path is exactly
one `$ref` line there, grouped by tag in the same order as the tags list and
API.md's section order.
